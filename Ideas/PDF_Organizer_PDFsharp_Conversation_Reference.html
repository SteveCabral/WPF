PDF Organizer / Viewer Application

Conversation reference: Visual Studio 2026, WPF, .NET 10, PDFsharp, and PDF page organization

This document consolidates the discussion about building a Windows desktop application that can open PDF files, preview their pages, reorder and add pages, filter pages by physical size, and save the resulting PDF.

1. Original Application Goal

The proposed application is a Windows desktop program that would allow the user to:

  • Open an existing PDF.
  • Preview all pages as thumbnails.
  • Click a thumbnail to see a larger preview.
  • Move/reorder pages.
  • Delete pages.
  • Add blank pages.
  • Insert pages from another PDF.
  • Filter pages by physical size, especially Letter and Legal.
  • Eventually save the modified document as a new PDF.
Core architectural idea: Build a real PDF application with its own PDF engine rather than making the program dependent on the Adobe Acrobat viewer.

3. Important Distinction: Acrobat vs. a PDF Engine

The initial question considered whether an application could interact with the PDF classes associated with an installed Adobe Acrobat PDF viewer.

There are two fundamentally different approaches:

Approach A — Automate Acrobat

Your WPF Application | | COM / OLE / Acrobat interfaces v Adobe Acrobat | v PDF

Adobe provides Acrobat SDK technologies for application integration. However, this approach makes the program dependent on Acrobat and on which Acrobat product is installed. Acrobat Reader also has much more limited automation capabilities than the full Acrobat product.

Approach B — Use a PDF library directly

Your WPF Application | v PDF Service | v PDF Library | v PDF

This is the recommended architecture. Acrobat can be installed on the computer, but the application does not need to use or control it.

Recommendation: Treat Acrobat as an optional PDF viewer installed on the machine, not as a dependency of the application.

6. PDF Rendering vs. PDF Editing

A key concept identified in the discussion is that PDF editing and PDF rendering are different jobs.

PDF page | +-- Text +-- Vector graphics +-- Images +-- Fonts +-- Transparency +-- Annotations +-- Forms | v PDF rendering engine | v Bitmap/image | v WPF Image control

The application needs a rendering path so it can turn a PDF page into an image suitable for a thumbnail or a large preview.

This is one reason the first implementation should be a small proof-of-concept rather than immediately building the entire application.

7. Letter and Legal Page Sizes

PDF page dimensions are normally represented in points.

72 points = 1 inch

US Letter:
8.5 × 11 inches
612 × 792 points

US Legal:
8.5 × 14 inches
612 × 1008 points

The application can inspect the page dimensions and classify each page.

public enum PageSizeCategory
{
    Letter,
    Legal,
    A4,
    Other
}

The filter then becomes a UI concern rather than something the PDF engine needs to understand:

The page-size classifier can also use a tolerance so that small floating-point or document-generation differences do not cause a page that is effectively Letter to be classified as Other.

8. Recommended Application Architecture

PDFOrganizer | +-- Models | +-- PdfDocumentModel | +-- PdfPageModel | +-- PageSizeCategory | +-- ViewModels | +-- MainViewModel | +-- PageViewModel | +-- FilterViewModel | +-- Views | +-- MainWindow.xaml | +-- PageThumbnail.xaml | +-- PdfPreview.xaml | +-- Services | +-- PdfService | +-- PdfRenderer | +-- FileService | +-- Commands +-- MovePageCommand +-- DeletePageCommand +-- InsertPageCommand +-- SaveCommand

This structure keeps PDF-specific code out of the visual controls and makes the application easier to extend later.

9. Page Ordering Model

A particularly useful design is to avoid rewriting the physical PDF file every time the user drags a page.

Instead, the application maintains the current page order in memory:

ObservableCollection<PdfPageViewModel>

For example:

Original:
1  2  3  4  5  6

User moves Page 5 before Page 3:

1  2  5  3  4  6

The PDF is rewritten only when the user chooses Save or Save As.

User drags page | v ObservableCollection changes | v UI immediately reflects new order | v User chooses Save | v PDFsharp creates the output PDF | v New PDF written to disk

This design also makes undo/redo much easier to implement later.

12. Why WPF Is a Good Fit

WPF provides several features that fit this application particularly well:

  • Data binding.
  • ObservableCollection.
  • MVVM support patterns.
  • ItemsControl and ListBox for page collections.
  • Image display.
  • Drag-and-drop interactions.
  • Commands.
  • Templates and styling.
  • Asynchronous operations.

The page-thumbnail area can therefore be treated as a bound collection rather than a collection of manually positioned controls.

14. Suggested Development Phases

Phase 1 — Viewer foundation

  1. Create WPF project.
  2. Target .NET 10.
  3. Install PDFsharp-WPF.
  4. Open a PDF.
  5. Count pages.
  6. Read page dimensions.
  7. Render one page.
  8. Display the page in a WPF control.

Phase 2 — Page thumbnails

  1. Render each page at thumbnail resolution.
  2. Create a page view model.
  3. Display thumbnails in a scrollable collection.
  4. Click a thumbnail to update the large preview.

Phase 3 — Page information and filtering

  1. Determine physical dimensions.
  2. Classify Letter, Legal, A4, and Other.
  3. Add All/Letter/Legal/A4 filters.
  4. Optionally add Portrait/Landscape filters.

Phase 4 — Page organization

  1. Delete pages.
  2. Drag and drop to reorder.
  3. Select multiple pages.
  4. Rotate pages.

Phase 5 — Page insertion and saving

  1. Add blank pages.
  2. Import pages from another PDF.
  3. Save As.
  4. Preserve the desired page order in the generated PDF.

Phase 6 — Advanced features

  1. Undo/redo.
  2. Extract selected pages.
  3. Combine PDFs.
  4. Import images as pages.
  5. Search.
  6. Bookmarks.
  7. Annotations.

15. Why Start With a Proof of Concept?

The most important technical question to validate early is page rendering.

A minimal test application should do only this:

Open PDF | v Count pages | v Read dimensions of every page | v Render Page 1 | v Display Page 1 in WPF

If this works correctly with representative PDFs, the rest of the application can be built around the result.

This is preferable to building the entire application first and discovering later that the rendering behavior, PDF compatibility, or performance is inadequate.

17. MigraDoc

Do not add MigraDoc simply because it appears alongside PDFsharp packages.

MigraDoc is primarily a high-level document generation/layout system. The proposed application is primarily concerned with opening, inspecting, rendering, reorganizing, importing, and saving existing PDF pages.

PDFsharp itself can be used independently of MigraDoc.

18. Licensing Consideration

PDFsharp is an open-source project and is attractive for this project because it avoids immediately committing to a commercial PDF SDK.

For a personal application, this is especially useful because development can begin without purchasing an enterprise PDF SDK.

Before distributing a commercial application, the exact license of the version and components used should always be reviewed directly from the project's current licensing documentation.

20. Current Recommendation

Recommended starting stack:
Visual Studio 2026 + C# + WPF + .NET 10 + PDFsharp-WPF 6.2.4 + MVVM.

23. Mental Model for the Project

The most useful way to think about the application is that it has three layers:

USER INTERFACE | v APPLICATION MODEL | v PDF ENGINE | v FILE

WPF handles what the user sees and interacts with.

MVVM/application logic handles page selection, ordering, filtering, commands, and application state.

PDFsharp handles the actual PDF document structures, pages, dimensions, importing, modification, and output.

This separation is the central design principle to preserve as the project grows.
